# 🧠 מדריך רקע — מה זה בעצם סוכן (Agent)?

זהו מסמך עזר למטלה — עזרה כדי שתתחילו מהמקום הנכון.
קריאה של 15 דקות.

---

## 1. מה זה סוכן, ומה הוא לא

**סוכן (Agent) הוא מודל שפה שרץ בלופ, עם גישה לכלים, שמחליט בעצמו מה לעשות בשלב הבא.**

זה כל הסיפור. ואת ההגדרה הזאת שווה לפרק:

| המושג | מה זה | הדוגמה מהקווסט |
|---|---|---|
| **קריאה בודדת ל-LLM** | שאלה → תשובה. אין כלים, אין מצב, אין לופ | "תנסח לי מייל התנצלות ללקוח" |
| **Workflow** | שרשרת צעדים ש**אתם** קבעתם בקוד. ה-LLM מבצע כל צעד, אבל הנתיב קבוע | `קרא הזמנה → קרא פרופיל → קרא מדיניות → החלט` — תמיד באותו סדר |
| **Agent** | ה-LLM מחליט **אילו** כלים לקרוא, **באיזה סדר**, ו**מתי לעצור** | "יש בעיה עם ההזמנה שלי" ⬅️ הסוכן מחליט מה הוא צריך לדעת |

ההבדל הקריטי הוא **מי קובע את זרימת הבקרה**. ב-workflow — אתם. בסוכן — המודל.

> 💡 **ההשלכה המעשית:** סוכן הוא כלי יקר יותר, איטי יותר וקשה יותר לדיבוג מ-workflow.
> Anthropic כותבים את זה במפורש בפוסט
> [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) —
> **התחילו מהפתרון הפשוט ביותר שעובד, והוסיפו אוטונומיה רק כשהיא נדרשת.** אם ידעתם
> מראש את סדר הצעדים, כתבתם workflow, וזה בסדר גמור.
>
> בקווסט הזה אנחנו מבקשים סוכן במפורש — כי בפניית תמיכה אמיתית אי אפשר לדעת מראש
> אם הבעיה היא במשלוח, בחיוב או במוצר, ולכן אי אפשר לקבע את הנתיב. אבל שווה שתבינו
> שזו החלטה, לא ברירת מחדל.

## 2. האנטומיה של סוכן

לכל סוכן, בכל פרימוורק, יש את חמישה החלקים האלה:

```
┌──────────────────────────────────────────────────┐
│  System Prompt   ← מי אתה, מה הסמכות שלך         │
├──────────────────────────────────────────────────┤
│  Tools           ← מה אתה יכול לעשות בעולם        │
├──────────────────────────────────────────────────┤
│  Memory          ← מה קרה עד עכשיו                │
├──────────────────────────────────────────────────┤
│  Stop Condition  ← מתי אתה מפסיק                  │
├──────────────────────────────────────────────────┤
│  Output Schema   ← באיזה פורמט אתה מחזיר תשובה    │
└──────────────────────────────────────────────────┘
```

והלופ עצמו — זה כל מה שקורה, שוב ושוב:

```
1. שלח למודל: system prompt + היסטוריה + רשימת הכלים
2. המודל מחזיר או טקסט, או בקשה להפעיל כלי (tool_use)
3. אם זה בקשת כלי:  הרץ את הפונקציה → החזר את התוצאה למודל → חזור ל-1
4. אם זה טקסט:      סיימנו
```

**זה 20 שורות קוד.** באמת. אפשר לכתוב את הלופ הזה לבד ב-Python, וזה אפילו מומלץ
לפני שנוגעים בפרימוורק — כדי להבין מה הפרימוורק עושה בשמכם. הפרימוורקים מוסיפים
retry, לוגים, זיכרון, טיפוסים ו-observability, לא קסם.

## 3. איך ה-LLM בוחר כלי — הנקודה שבה רוב האנשים נכשלים

זו הנקודה החשובה ביותר במסמך הזה.

**המודל לא רואה את הקוד שלכם.** הוא רואה רק את השם, התיאור וסכמת הקלט של כל כלי.
זה הכל. כשמעבירים כלים ל-API, מה שנשלח נראה כך:

```json
{
  "name": "check_return_policy",
  "description": "Evaluate whether an order is still eligible for a return or refund. Applies the return window, VIP overrides, non-returnable categories and order-status rules, and returns the verdict together with the policy ids behind it. Call this before promising the customer anything.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "Order identifier, e.g. 'ORD-1003'."},
      "reason": {"type": "string", "enum": ["damaged_on_arrival", "wrong_item", "..."]}
    },
    "required": ["order_id"]
  }
}
```

התיעוד של Anthropic ב-[Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
אומר את זה בלי להתחכם: **התיאור הוא הגורם החשוב ביותר בביצועי הכלי.** ההמלצה שלהם
היא 3–4 משפטים לכל כלי לפחות, שמכסים:

- מה הכלי עושה
- **מתי להשתמש בו — ומתי לא**
- מה כל פרמטר אומר ואיך הוא משפיע
- מה הכלי **לא** מחזיר

השוו:

| ❌ תיאור גרוע | ✅ תיאור טוב |
|---|---|
| `"Gets the policy for an order."` | `"Evaluate whether an order is still eligible for a return or refund... Call this before promising the customer anything."` |

התיאור הגרוע משאיר את המודל עם שאלות: זה מחזיר טקסט? verdict? האם אני אמור לקרוא
לזה לפני או אחרי הזיכוי? התוצאה היא סוכן שקורא לכלי הלא נכון, או שלא קורא בכלל.

> 🔧 **המסקנה המעשית:** אם הסוכן שלכם בוחר כלי לא נכון — **התיקון הוא בתיאורי הכלים,
> לא ב-system prompt.** זה הרפלקס ההפוך ממה שרוב האנשים עושים.
>
> במארז שקיבלתם, ה-docstrings כבר כתובים ככה, ו-`TOOL_SCHEMAS` נותן לכם את הסכמות
> מוכנות. הריצו `GET /tools/schemas` בשרת התיעוד ותראו בעצמכם מה המודל רואה.

## 4. סקיל מול סוכן — ההבדל שמבלבל את כולם

שני המושגים נשמעים דומים ופותרים בעיות שונות לגמרי.

**Skill** = חבילת **ידע והוראות** שנטענת לתוך ההקשר של המודל **הנוכחי**.
**Agent / Subagent** = **הקשר נפרד**, עם prompt וכלים משלו, שמבצע משימה ומחזיר תוצאה.

| | 🧩 Skill | 🤖 Agent / Subagent |
|---|---|---|
| **מה זה מרחיב** | מה שהמודל **יודע לעשות** | **מי** עושה את זה |
| **הקשר (Context)** | נטען לתוך אותו חלון הקשר | חלון הקשר **נפרד** לגמרי |
| **מבנה** | תיקייה עם `SKILL.md` + קבצי עזר וסקריפטים | הגדרה עם system prompt + סט כלים + מודל |
| **מה חוזר** | ההוראות מצטרפות לשיחה, המודל ממשיך | תשובה מסוכמת בלבד. הרעש נשאר בפנים |
| **מתי נטען** | כשה-`description` שלו מתאים לבקשה | כשהמשימה מתאימה לתיאור הסוכן |
| **טוב ל-** | "ככה עושים X בחברה שלנו", תבניות, נהלים חוזרים | משימה שתציף את השיחה הראשית ברעש; הגבלת כלים |
| **דוגמה** | סקיל שיודע ליצור מצגות PowerPoint | סוכן חוקר שקורא 40 קבצים ומחזיר 3 שורות |

### מנגנון ה-Skill — Progressive Disclosure

זה החלק המתוחכם. סקיל לא נטען כולו מראש, אלא בשלושה שלבים:

| שלב | מה נטען | מתי | עלות |
|---|---|---|---|
| 1 | `name` + `description` מה-YAML frontmatter | תמיד, בעליית הסשן | ~100 טוקנים לסקיל |
| 2 | גוף ה-`SKILL.md` — ההוראות | כשהסקיל מופעל | פחות מ-5k טוקנים |
| 3 | קבצי עזר וסקריפטים | רק כשמפנים אליהם בפועל | 0 עד שניגשים |

המשמעות: אפשר להתקין עשרות סקילים בלי לשלם על ההקשר, כי עד שסקיל מופעל — רק השם
והתיאור שלו תופסים מקום. ולסקריפט שהסקיל מריץ, הקוד **לא** נכנס להקשר בכלל, רק הפלט.

> שימו לב לתבנית החוזרת: **בסקיל, כמו בכלי, ה-`description` הוא הממשק.** הוא צריך
> לומר גם *מה* הסקיל עושה וגם *מתי* להשתמש בו. אותו עיקרון בדיוק.

### ומה עם Tools ו-MCP?

כדי שהתמונה תהיה שלמה — ארבע שכבות, ארבע בעיות שונות:

| | מה זה נותן |
|---|---|
| **Tool** | יכולת לבצע פעולה בעולם: לקרוא DB, לשלוח מייל, להחזיר כסף |
| **Skill** | ידע ונהלים: איך אנחנו עושים דברים כאן |
| **Subagent** | הקשר נפרד + סט כלים מוגבל, מחזיר תוצאה מסוכמת |
| **MCP** | פרוטוקול סטנדרטי לחיבור כלים חיצוניים, כדי לא לכתוב אינטגרציה לכל מערכת |

**בקווסט הזה אתם בונים Agent שמשתמש ב-Tools.** אין סקילים ואין MCP. אבל שווה להכיר
את המפה, כי בראיון עבודה ישאלו אותכם על ההבדל.

## 7. ⚠️ מלכודות נפוצות

| המלכודת | מה קורה | התיקון |
|---|---|---|
| **Docstring עמום** | הסוכן קורא לכלי הלא נכון, או לא קורא בכלל | תיאור של 3–4 משפטים שאומר גם *מתי לא* להשתמש בכלי |
| **Guardrail בפרומפט בלבד** | "אל תאשר מעל $50" — והמודל בכל זאת מאשר | הגבלה בקוד. `process_refund` במארז שלכם עושה את זה |
| **הזיית נתונים** | הסוכן ממציא תאריך משלוח מול הזמנה שלא קיימת | הכלים מחזירים `{"error": ...}` — לימדו את הסוכן לזהות את המפתח הזה ולעצור |
| **לופ אינסופי** | הכלי מחזיר שגיאה, הסוכן מנסה שוב, ושוב, ושוב | `max_iterations` + התנהגות מוגדרת אחרי שגיאה |
| **פלט לא מובנה** | פרסינג של תשובה בעזרת regex ותפילה | structured output / response model אמיתי של הפרימוורק |
| **פער בין ההחלטה לתשובה** | הכלי החזיר `ESCALATION_REQUIRED`, והלקוח קיבל "הזיכוי בוצע" | הרכיבו את התשובה ללקוח **מתוך** תוצאת הכלי, לא מתוך מה שהמודל זוכר |
| **לזרוק exception על בעיה עסקית** | הסוכן קורס במקום להתאושש | בעיה עסקית = דאטה. `TypeError` = באג בקוד |

## 8. איך יודעים שהסוכן באמת עובד

לא לפי "רץ אצלי". לפי שלוש שאלות:

1. **האם הוא מגיע לתשובה הנכונה בשלושת תרחישי הקצה?** אישור, הסלמה, דחייה.
2. **האם שרשרת החשיבה מסבירה את ההחלטה במספרים ובסעיפים אמיתיים** שנקראו מהכלים,
   או שהיא ניסוח כללי שיכול להתאים לכל מקרה?
3. **האם הוא נכשל בכבוד?** מול הזמנה שלא קיימת, מול סכום שלילי, מול פנייה מבולבלת.

התשובה לשלושתן נמצאת ב-`examples/scenarios.md` שקיבלתם. הריצו את הסוכן על כל תשעת
התרחישים, לא רק על השלושה שהמסמך דורש.
