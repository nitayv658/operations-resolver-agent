## 🎯 המטרה של האתגר הדו-שלבי

לאחר שביססתם לוגיקת **סוכן בודד** בשלב א', אנו מעלים הילוך. בעולם האמיתי, סוכן
יחיד נוטה להגיע לעומס קוגניטיבי — "הזיות" ובלבול — כשהמשימה מורכבת מדי.

בחלק ב' נלמד וניישם **צוות סוכנים מתמחים** (Multi-Agent System) העובדים בתיאום,
מעבירים מקל ומידע ביניהם, ומבצעים משימות מקצה לקצה.

---

## 1. 💡 הסבר ורקע עסקי

בשלב זה, חברת **GlobalCart** מרחיבה את מערך האוטומציה. במקום סוכן אחד שמנסה לעשות
הכל, אנו מקימים **צוות משימה תפעולי** (Operations Crew) שבו כל סוכן הוא מומחה
בתחומו: חקירה והונאות, קבלת החלטות, ותקשורת/הסלמה.

**האתגר המרכזי בשלב זה אינו רק הפעלת הכלים**, אלא ניהול הזיכרון (Memory Context),
העברת המידע בין הסוכנים, ומניעת לולאות אינסופיות (Infinite Loops).

---

## 2. 📝 המשימה של חלק ב'

עליכם להרחיב את המערכת ולהקים צוות המורכב מ**3 סוכנים שונים לפחות**, המעבירים
מידע מובנה ביניהם:

### Agent 1 — The Researcher & Fraud Auditor (סוכן החקירה והבטיחות)
**תפקיד:** שולף נתוני הזמנה ומשתמש, ומבצע בדיקת הונאות (Fraud Detection)
אלגוריתמית על בסיס חוקים עסקיים.
**פלט:** דו"ח הערכת סיכונים ונתונים גולמיים.
**כלים:** `get_order_details`, `get_user_profile`, `audit_fraud_risk`

### Agent 2 — The Decision Maker / Operations Lead (סוכן קבלת ההחלטות)
**תפקיד:** מקבל את הדו"ח מסוכן 1, מתייעץ עם מדיניות החברה, ומכריע על הפתרון העסקי
והכספי.
**פלט:** החלטה תפעולית סופית.
**כלים:** `check_return_policy`, `process_refund`

### Agent 3 — The Communications & Escalation Manager (סוכן התקשורת והדיווח)
**תפקיד:** מנסח תשובה מותאמת אישית ללקוח, ובמקרה של הסלמה/חשד להונאה מפיק התראה
מובנית ומזריק אותה לערוץ חיצוני (Slack/Telegram).
**פלט:** הודעה מנוסחת ללקוח + הזרקת התראה למערכת חיצונית.
**כלים:** `get_escalation_route`, `send_slack_alert`

> **שימו לב מה אין לכל סוכן.** לסוכן 3 אין גישה ל-`process_refund`. לסוכן 1 אין
> יכולת לאשר כספים או לשלוח הודעות. זה לא קוסמטי — זה ה-guardrail הזול ביותר
> במערכת, והמארז מספק לכם את שלוש החבילות מוכנות.

## 3. 📦 הפרטים והקבצים שמקבלים מראש

בנוסף לקבצים מחלק א' (שמצורפים כאן במלואם), מתווספים קבצים ייעודיים לתקשורת
ובדיקת סיכונים:

| קובץ | מה יש בו | למה זה משמש |
|---|---|---|
| `data/fraud_rules.json` | 8 חוקים משוקללים לזיהוי סיכונים: ריבוי פניות, החלפת כתובת ברגע האחרון, חשבון חדש בסכום גבוה ועוד. 3 רמות סיכון | המנוע שסוכן 1 מפעיל. כל חוק עם `rule_id` שאפשר לצטט |
| `data/escalation_channels.json` | 4 ערוצי ניתוב עם תנאי הפעלה, SLA ותבניות הודעה | קובע לאן סוכן 3 מעביר את המקרה |

## 4. 💡 מספר טיפים לפני שמתחילים

**בחירת פרימוורק מתאים.** מומלץ מאוד לעבוד עם פרימוורקים ייעודיים לצוותי סוכנים
כגון **CrewAI**, **LangGraph**, או **Microsoft AutoGen**. יש מסמך רקע מסודר
בתיקיית `Shared/`:
[מדריך - צוות סוכנים (חלק ב)](../Shared/מדריך%20-%20צוות%20סוכנים%20(חלק%20ב).md).

**תכנון מעבר המידע (Data Flow).** הגדירו מבני נתונים ברורים (Pydantic / TypedDict)
להעברת המידע מסוכן 1 לסוכן 2 ולסוכן 3. כל הכלים מחזירים dict שטוח וסריאליזבילי,
כך שהם נכנסים ישר למודל Pydantic. ה-README של המארז מציע שתי סכמות התחלה.

**מניעת לולאות אינסופיות.** הגדירו מנגנון עצירה (Max Iterations / Stop Conditions)
למקרה שהנתונים חסרים או לא עקביים. הגדירו גם **מה קורה** כשהדו"ח מסוכן 1 חסר —
הסלמה היא תשובה טובה, שליחה חוזרת של סוכן 1 בלופ היא לא.

**המלכודת המרכזית של חלק ב'.** התרחיש `ORD-1005` הוא תביעה **לגיטימית לחלוטין** —
`check_return_policy` מחזיר `ELIGIBLE`. אבל מנוע ההונאות מחזיר 90/100 ו-band
`high`. צוות שקורא רק את פסק המדיניות מאשר תשלום לתביעה חשודה. רק דו"ח הסיכונים
עוצר את זה.

**אל תשלחו התראה על תרחיש נקי.** כש-`get_escalation_route` מחזיר
`escalation_required: false` — שלחו את התשובה ללקוח ואל תשלחו התראה. סוכן תקשורת
שמציף את `#fraud-security` על כל פנייה הוא כשל אמיתי, ואנחנו קוראים את ה-outbox.

**התשובה ללקוח לא חושפת את דגל ההונאה.** לא מאשימים לקוח בהונאה. "הבקשה בבדיקה
ונחזור אליך" — כן. "זיהינו אצלך דפוס חשוד" — לא.

## 5. 🛠️ גישת מימוש מומלצת

**אחריות מוגדרת (Separation of Concerns).** כל סוכן בצוות מקבל גישה רק לכלים
הרלוונטיים לתפקידו — למשל, סוכן הדיווח מקבל גישה רק ל-`send_slack_alert`
ול-`get_escalation_route`. המארז מספק את זה מוכן:

```python
import multi_agent_tools as mat

researcher_tools = mat.RESEARCHER_TOOLS   # 3 כלים
decision_tools   = mat.DECISION_TOOLS     # 2 כלים
comms_tools      = mat.COMMS_TOOLS        # 2 כלים
```

ושווה לכתוב על זה בדיקה:

```python
assert "process_refund" not in {t["name"] for t in mat.COMMS_TOOLS}
```

**סדר פעולות טורי/מקבילי.** הגדירו זרימה ברורה:

```
[Customer Ticket] ➡️ Agent 1 (Fraud) ➡️ Agent 2 (Decision) ➡️ Agent 3 (Comms) ➡️ [Email/Alert]
```

**מנוע ההונאות הוא מנוע חוקים, לא דעה.** `audit_fraud_risk` דטרמיניסטי. אל תבקשו
מהמודל להעריך ציון סיכון בעצמו, ואל תתנו לו לבטל את ה-band שהמנוע החזיר. העבירו
את הדו"ח **בשלמותו** לסוכן 2 — `triggered_rules` ו-`evidence` הם מה שהופך את
ההחלטה הסופית לניתנת לביקורת.

**Slack עובד גם בלי Slack.** `send_slack_alert` כותב ל-`outbox/alerts.jsonl` כברירת
מחדל, כך שאפשר לסיים את כל הקווסט בלי workspace. לסרטון ההדגמה, כדאי לחבר webhook
אמיתי:

```bash
export SLACK_WEBHOOK_URL="https://hooks.slack.com/services/..."
```

## 6. 📤 כיצד להגיש את המטלה

יש להגיש את התוצרים הבאים:

- [ ] **קישור ל-GitHub Repository** המכיל מימוש מלא של ה-Multi-Agent Crew System.
- [ ] **קובץ `README.md` מפורט**, הכולל:
  - [ ] **דיאגרמת זרימה (Architecture Flowchart)** המציגה את מעבר המידע בין
        הסוכנים — Mermaid, ASCII או תמונה, כולם קבילים. הדיאגרמה צריכה להראות לא
        רק מי הסוכנים אלא **מה עובר ביניהם**.
  - [ ] הסבר על **ניהול הזיכרון (Memory Context)** — כיצד המידע נשמר ועובר בין
        שלב לשלב, ואילו מבני נתונים הגדרתם.
  - [ ] **מנגנוני הגנה (Guardrails)** — הסבר כיצד המערכת מונעת חריגת סמכות כספית
        ומניעת לולאות אינסופיות, ואיפה בקוד זה נאכף.
- [ ] **סרטון הדגמה (Loom)** — סרטון **עד 3 דקות** המציג **תרחיש חשד להונאה מורכב**
      והסלמה אוטומטית לערוץ Slack/Telegram.

**לפני ההגשה — בדקו את עצמכם:**

```bash
python3 examples/verify_scenarios.py     # הדאטה והמנועים תקינים?
```

ואז הריצו את הצוות על התרחישים ב-`examples/scenarios.md`, וודאו שלא נסוגתם
בתרחישי חלק א'.

⚠️ **אל תקומיטו מפתחות API או webhook אמיתי לריפו.** השתמשו ב-`.env`
וב-`.gitignore`.
